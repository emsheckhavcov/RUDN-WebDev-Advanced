## Context

См. `proposal.md` — Why; поведенческие требования зафиксированы в `specs/board-card-counter/spec.md`.

Сейчас `App` в `client/src/App.tsx` загружает полный список карточек запросом React Query с ключом `["cards"]` через `fetchCards` из `client/src/api/cards.ts`. Этот список передаётся в `BoardColumn`, где `hideDone` используется только для формирования `visibleCards`. `BoardHeader` пока не получает данные о карточках. После успешного создания карточки `NewCardForm` инвалидирует ключ `["cards"]`, и запрос обновляется.

## Goals / Non-Goals

**Goals:**

- Использовать уже загруженный в `App` список карточек как единственный источник общего количества.
- Передать в заголовок состояние загрузки и число, вычисленное по полному списку карточек.
- Не связывать общий счётчик с фильтром, который применяется внутри `BoardColumn`.
- Сохранить обновление счётчика через существующую инвалидацию запроса после добавления карточки.

**Non-Goals:**

- Менять API, модель карточки, React Query или Zustand.
- Переносить фильтрацию выполненных карточек либо состояние фильтра в `App` или `BoardHeader`.
- Добавлять отдельный запрос или состояние для счётчика.
- Изменять поведение формы создания карточки или обработку ошибок загрузки.

## Decisions

### Передавать число и состояние загрузки из `App` в `BoardHeader`

`App` передаёт `BoardHeader` число карточек, вычисленное как длина загруженного полного массива, и текущий флаг `isLoading`. `BoardHeader` остаётся презентационным компонентом: рядом с названием он выводит `…`, пока список загружается, и переданное число после загрузки. Пустой загруженный массив даёт число `0`.

**Рассмотренные варианты:**

- **Выбранный — вычислять число в `App` и передавать через props.** `App` уже владеет результатом запроса; это использует существующий источник данных, делает состояния загрузки и результата явными и не добавляет сетевых запросов.
- **Отклонённый — загружать карточки отдельно из `BoardHeader`.** Это дублировало бы запрос и серверное состояние, усложнило бы согласование счётчика и колонки после добавления карточки и создало бы лишнюю нагрузку.
- **Отклонённый — вычислять число из `visibleCards` в `BoardColumn`.** Этот массив уже отфильтрован по `hideDone`, поэтому такой счётчик не учитывал бы выполненные карточки и не соответствовал бы требованию общего количества.

### Считать полный список, не результат фильтра

Число вычисляется до фильтрации в `BoardColumn` — по исходному массиву, возвращённому `fetchCards`. Состояние `hideDone` остаётся локальным для поведения отображения колонки и не влияет на значение, переданное заголовку.

### Использовать текущую инвалидацию запроса для обновления

После успешного создания карточки `NewCardForm` уже инвалидирует `["cards"]`. React Query обновляет данные, `App` получает новый полный список и передаёт новое число в `BoardHeader`. Отдельное обновление кэша или новый запрос не требуются.

## Risks / Trade-offs

- [Пропсы связывают `App` и `BoardHeader` состоянием запроса] → Это небольшая явная зависимость для данных, уже принадлежащих `App`; она предпочтительнее скрытого повторного запроса из заголовка.
- [Отдельное состояние ошибки загрузки не входит в эту задачу] → Не менять существующую обработку ошибок; требования для счётчика определяют состояние загрузки и успешно загруженный пустой список.

## Migration Plan

Миграция данных и API не требуется. Изменение ограничивается передачей данных между существующими клиентскими компонентами; откат сводится к удалению отображения счётчика и передаваемых ему props.
