## Context

См. `proposal.md` — мотивация и объём изменения; `specs/card-completion/spec.md` — обязательное поведение и HTTP-контракт. Сервер уже разделён на роутер, middleware, контроллер и сервис карточек. Сервис хранит массив карточек в памяти, а клиент загружает его через React Query с ключом `["cards"]`. Vite proxy преобразует клиентский путь `/api/cards/:id` в серверный `/cards/:id`.

## Goals / Non-Goals

**Goals:**

- Изменять только `isDone` существующей карточки, сохраняя её остальные поля.
- Сохранить границу слоёв: сервис оперирует карточками и результатом операции, HTTP-ответы формирует контроллер.
- После успешного изменения обновлять отображаемый список через существующий источник данных React Query.

**Non-Goals:**

- Добавлять постоянное хранилище, менять схему карточки или менять существующие GET, POST и DELETE контракты.
- Использовать оптимистическое обновление, хранить копию карточек в клиентском состоянии или менять фильтр выполненных карточек.

## Decisions

### Использовать PATCH для изменения одного поля

Клиент отправляет `PATCH /api/cards/:id` с JSON-телом `{ "isDone": boolean }`; proxy направляет запрос на `PATCH /cards/:id`. `PATCH` подходит для частичного обновления одного поля и не требует отправлять остальные поля карточки.

Альтернатива — `PUT /cards/:id` — обычно описывает замену всего ресурса и потребовала бы передавать полную карточку либо вводить неоднозначную семантику частичной замены. Отдельный путь вроде `/cards/:id/done` также возможен, но не нужен: изменяемое поле однозначно задаётся телом запроса.

### Сохранить последовательность router → middleware → controller → service

Роутер подключает middleware проверки `isDone` перед контроллером. Middleware принимает только boolean, включая `false`; отсутствующее поле или значение другого типа завершает запрос JSON-ответом `400` и не вызывает контроллер. Контроллер получает `id` из URL и проверенное значение из тела, затем вызывает асинхронную функцию сервиса.

Сервис находит карточку и меняет только её `isDone`. Он возвращает обновлённую карточку либо сигнал отсутствия карточки и не импортирует Express, не работает с `req`/`res` и не выбирает HTTP-статусы. Контроллер преобразует результат: при отсутствии карточки возвращает JSON `404`, иначе — `200` с полной обновлённой карточкой. Такой порядок оставляет валидацию входного HTTP-запроса в middleware, а решение о статусе `404` — в контроллере.

### Обновлять React Query инвалидацией после успеха

Компонент карточки отправляет мутацию через функцию клиентского API. После успешного ответа он вызывает `invalidateQueries({ queryKey: ["cards"] })`; список повторно загружается существующим query и остаётся единственным источником состояния карточек. Во время запроса элемент управления блокируется; при ошибке показывается сообщение, а кэш не инвалидируется.

Альтернатива — оптимистически менять кэш до ответа сервера. Инвалидация проще, совпадает с текущим подходом создания и удаления карточек и не требует отката локального состояния при ошибке.

## Risks / Trade-offs

- [Состояние сервиса хранится в памяти и теряется при перезапуске процесса] → Это существующее ограничение приложения; в рамках изменения требуется сохранение после повторной загрузки доски при работающем сервере, а не постоянное хранилище.
- [После успешной мутации список зависит от повторного GET] → Сохранять текущий кэш карточек при ошибке повторной загрузки и показывать ошибку мутации; постоянное оптимистическое или локальное состояние не вводить.

## Migration Plan

Миграция данных не нужна: поле `isDone` уже есть в карточках. Развернуть сервер с новым маршрутом и middleware вместе с клиентом, который использует PATCH; старые эндпоинты остаются без изменений. Для отката вернуть предыдущие версии сервера и клиента; отдельное преобразование данных не требуется.
