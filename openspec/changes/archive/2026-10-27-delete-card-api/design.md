## Context

См. `proposal.md` — Why. Спецификация в `specs/card-deletion/spec.md` фиксирует пользовательское поведение, HTTP-статусы и формат ответов. Сервер в `server/index.ts` хранит карточки в памяти и уже предоставляет GET и POST; клиент отправляет DELETE на `/api/cards/:id`, а Vite proxy удаляет префикс `/api`, направляя запрос на `/cards/:id`.

## Goals / Non-Goals

**Goals:**

- Удалять только карточку, совпавшую с параметром URL, и сохранять существующие GET/POST.
- Возвращать предсказуемые JSON-ошибки для отсутствующей карточки, неизвестного маршрута и необработанной ошибки.
- Оставить клиент и формат карточки без изменений.

**Non-Goals:**

- Добавлять постоянное хранилище, новые зависимости или клиентские изменения.
- Изменять поведение подтверждения и отображения карточки в клиенте.
- Реализовывать другие методы API или менять формат существующих ответов.

## Decisions

### Удалять элемент из существующего массива по точному `id`

Маршрут `DELETE /cards/:id` находит индекс карточки по `req.params.id`. Если совпадения нет, он возвращает `404` с JSON; иначе удаляет ровно один элемент и отвечает `204` без тела.

Альтернатива — фильтровать массив и сравнивать его длину до и после. Она тоже возможна, но индекс и `splice` явно удаляют одну найденную карточку и позволяют отличить отсутствие id до изменения данных.

### Разделить ответы для неизвестного маршрута и исключений

После прикладных маршрутов устанавливается middleware неизвестного маршрута, возвращающий JSON `404`; за ним — error middleware с четырьмя параметрами, возвращающий общий JSON `500`. Error middleware записывает исходную ошибку в серверный журнал, но не раскрывает детали исключения в HTTP-ответе.

Альтернатива — оставить стандартную HTML-страницу Express для неизвестных URL либо обрабатывать ошибки внутри каждого маршрута. Первый вариант нарушает единый JSON-контракт, второй дублирует обработку и пропускает неожиданные исключения.

### Сохранить клиентскую интеграцию

Клиентский proxy преобразует `/api/cards/:id` в `/cards/:id`, а клиент считает любой успешный HTTP-статус успешным удалением. Ответ `204` совместим с существующим `deleteCard`, который не читает тело ответа; инвалидация React Query после успеха остаётся без изменений.

## Risks / Trade-offs

- [Данные находятся только в памяти и сбрасываются при перезапуске процесса] → Это существующее ограничение сервера и не меняется в рамках задачи.
- [Общий ответ `500` скрывает подробности ошибки от клиента] → Подробности остаются в серверном журнале, а клиент получает стабильный безопасный JSON-ответ.

## Migration Plan

Миграция клиентского кода не требуется. Развернуть сервер с новыми маршрутами; откат состоит в возврате серверного файла к предыдущей версии. Существующие GET/POST и структура карточки остаются прежними.
