## Context

См. `proposal.md` — Why; пользовательское поведение и сценарии удаления, подтверждения, отмены и ошибки описаны в `specs/card-deletion/spec.md`.

Сейчас `App` загружает полный список карточек через React Query по ключу `["cards"]` с помощью `fetchCards` из `client/src/api/cards.ts`, а затем передаёт его в `BoardColumn`. Колонка фильтрует список по `hideDone` и создаёт `BoardCard` для каждой видимой карточки, но передаёт ей только `title` и `isDone`, хотя у каждой карточки есть `id`. `NewCardForm` служит существующим примером mutation: использует `useMutation` и после успешного изменения инвалидирует запрос `["cards"]`. API-функции удаления пока нет.

## Goals / Non-Goals

**Goals:**

- Удалять выбранную карточку по её `id` через API и сохранять результат на сервере.
- Обновлять отображаемый список через общий кэш карточек, без перезагрузки страницы.
- Запрашивать подтверждение до отправки запроса и не менять список при отмене или ошибке.
- Показывать пользователю понятную ошибку, если удаление не удалось.

**Non-Goals:**

- Добавлять новый серверный маршрут или изменять модель карточки.
- Использовать оптимистичное удаление или отдельное клиентское хранилище списка.
- Менять фильтр карточек и поведение создания карточек.

## Decisions

### Использовать мутацию на карточке и общий запрос списка

`BoardColumn` передаёт `card.id` в `BoardCard` вместе с уже передаваемыми данными. В `BoardCard` действие удаления вызывает `window.confirm` с вопросом об удалении карточки. Если пользователь отменяет подтверждение, обработчик завершает работу без вызова мутации и без сетевого запроса.

После подтверждения `useMutation` вызывает новую API-функцию `deleteCard(id)` из `client/src/api/cards.ts`. Функция отправляет `DELETE /api/cards/{id}` и отклоняет Promise при неуспешном HTTP-ответе, чтобы React Query перевёл мутацию в состояние ошибки. На успехе `onSuccess` инвалидирует `["cards"]`; существующий запрос в `App` загружает актуальный список, и удалённая карточка исчезает с доски без перезагрузки страницы. Сервер остаётся источником истины, поэтому после перезагрузки карточка не возвращается.

При ошибке мутация не инвалидирует список и не удаляет карточку локально. `BoardCard` использует состояние ошибки мутации для показа сообщения рядом с действием удаления. Пока запрос выполняется, кнопку удаления следует блокировать, чтобы избежать повторных запросов для той же карточки.

### Рассмотренные варианты

- **Выбранный — `useMutation` в `BoardCard`, `deleteCard(id)` и инвалидация `["cards"]` после успеха.** Действие и его состояние ошибки располагаются рядом с конкретной карточкой; список обновляется через уже используемый общий запрос. Это повторяет установленный в `NewCardForm` паттерн React Query и не требует второго источника состояния или механизма отката.
- **Отклонённый — оптимистично удалять карточку из кэша до ответа сервера.** Это требует сохранять предыдущий кэш и восстанавливать его при ошибке; без этого UI может сообщить об ошибке, но оставить карточку скрытой. Для текущего потока подтверждённое сервером удаление с последующей инвалидацией проще и надёжнее.
- **Отклонённый — поручить удаление родителю (`BoardColumn` или `App`) и передать callback в карточку.** Это перемещает состояние мутации и сообщение об ошибке дальше от элемента, который инициирует действие, и добавляет промежуточный callback. Для текущего компонента и существующего локального паттерна это не даёт преимущества.

### Подтверждать удаление через `window.confirm`

Использовать встроенный синхронный `window.confirm` с названием карточки в тексте запроса. Мутация запускается только при результате `true`. При `false` обработчик не меняет UI и не обращается к API. Это удовлетворяет сценарию отмены без добавления зависимости или собственного диалога.

### Явно обрабатывать отказ API

`deleteCard` проверяет `response.ok`, как существующие `fetchCards` и `createCard`, и выбрасывает ошибку удаления при неуспешном ответе. Ошибка остаётся в состоянии `useMutation`; компонент отображает её, а исходный список остаётся видимым, поскольку инвалидация выполняется только после успешного удаления.

## Risks / Trade-offs

- [Встроенный `window.confirm` блокирует взаимодействие со страницей и зависит от браузера] → Это простой нативный способ подтверждения без новой UI-инфраструктуры; отдельный диалог можно рассмотреть позже, если появятся требования к единому стилю.
- [Инвалидация после успеха требует повторного запроса списка] → Использовать уже настроенный React Query и существующий API; для размера текущего списка это предпочтительнее оптимистического кэша с логикой отката.
- [Ошибка запроса должна быть заметна пользователю] → Рендерить доступное текстовое сообщение у карточки и не скрывать её до подтверждённого успеха.

## Migration Plan

Миграция данных и изменение API-сервера не требуются: mock-сервер уже обслуживает коллекцию карточек. Добавить клиентский запрос удаления по `id`, передать `id` в `BoardCard` и связать успешную мутацию с инвалидацией `["cards"]`. Для отката удалить действие и mutation; карточки и API чтения/создания останутся без изменений.
